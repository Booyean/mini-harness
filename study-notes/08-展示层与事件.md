# 第 8 层 · 展示层与事件总线 学习笔记

> 文件：agent/events.py（16 行）、ui/tui.py（126 行）

## 一、EventBus 发布-订阅（events.py）

```python
class EventBus:
    def __init__(self): self._handlers = {}
    def on(self, event_type, handler):   # 订阅
        self._handlers.setdefault(event_type, []).append(handler)
    def emit(self, event_type, **data):  # 广播
        for handler in self._handlers.get(event_type, []):
            handler(**data)
DEFAULT_BUS = EventBus()  # 全局单例
```

- 核心：loop 只"喊事实"（emit），谁关心谁订阅（on）。
- 解耦：loop 完全不知道 UI 存在。

## 二、完整数据流闭环

```
第1层 stream_chat_full yield "text"
  → 第2层 loop.py:156 bus.emit("text", content=片段)
  → 第8层 tui.py:58 _on_text → console.print
```

- 终端逐字显示 = 生成器产出 → loop 转发事件 → UI 订阅渲染。
- 6 种事件（tui.py:10-16）：text/tool_call/tool_result/context_trimmed/
  compact_start/assistant_done，与 loop 的 bus.emit 一一对应。

## 三、diff 高亮分工

- loop 生产 diff（执行工具前后读 old/new，unified_diff）→ 事件传出。
- tui 只负责着色（+/绿 -/红 @@/青 其他/dim）。
- 原则：数据生产与数据展示解耦；UI 不碰文件系统。

## 四、_SilentBus：可注入接口的价值

- 空实现 on/emit，子代理 emit 进黑洞，不刷主界面。
- run_loop 预留 events 参数（loop.py:90-93 bus = events or DEFAULT_BUS）。
- 不改 loop，换 bus 实现就改行为：显示/静默/记日志/推 Web。

## 五、交互细节

- setup_console 先于主循环调用（main.py:323）：订阅必须先于发布。
- on 是 append 不幂等：重复 setup → handler 重复 → 一条消息打印两次。
- _on_text 用 markup=False：防 AI 输出里的 [bold] 被 rich 误解析。

## 六、思考题与答案

**Q1：loop 直接 print 不行吗？为什么要有事件总线？**
A：直接 print 把大脑和脸焊死。事件总线带来三点：① 解耦——loop 只 emit
事实，不关心谁渲染；② 多订阅者——同一事件可挂日志、测试、Web 推送等
多个 handler，加功能不改 loop；③ 可注入——换 bus 实现（_SilentBus）
即切换行为，run_loop 零改动。这是发布-订阅模式的经典收益。

**Q2：DEFAULT_BUS 用全局单例，有什么利弊？**
A：利：简单，跨模块共享一个总线无需传参。弊：全局可变状态——
测试难隔离（多次测试共享同一 handlers），多会话并发会互相污染
（一个会话的事件发到另一个会话的 UI）。生产系统倾向依赖注入：
run_loop 的 events 参数正是为此预留的注入点。

**Q3：diff 为什么要 loop 算、tui 渲染？tui 自己读文件算不行吗？**
A：职责分离。loop 执行工具前后天然持有 old/new 文件内容，算 diff 是它
流程的零成本副产物；tui 若自己算，要重复读文件（重复 IO）、且 UI 层
不该碰文件系统。正确分工：数据生产（loop）→ 事件传递 → 数据展示（tui）。
各层只做自己擅长的事。

**Q4：_SilentBus 为什么用"空实现 on/emit"就能静默，而不是特判？**
A：因为 run_loop 只调 bus.emit 发事件、从不读 bus 内容。传入 emit 空实现
的 bus，事件就"发到黑洞"。这体现事件总线作为"可注入接口"的力量：
不需要在 loop 里写 if 判断"要不要显示"，换一个 bus 实现即可。

**Q5：setup_console 为什么必须先于主循环、且只调一次？**
A：① 订阅先于发布——loop 在 while 里反复 emit，若订阅晚于 emit，前面的
事件无人接收而丢失。② on 是 append 语义（非覆盖、非幂等），重复 setup
会重复注册 handler，导致同一事件触发多个处理器、一条消息打印两次。
所以"先注册、只注册一次"。
