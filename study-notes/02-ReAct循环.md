# 第 2 层 · ReAct 循环 学习笔记

> 文件：agent/loop.py（266 行，全书心脏）
> 对照脚本：day4_demo.py

## 一、ReAct 概念

- 模型单次调用只能输出"话"或"工具单"，无法自己干活、看不到结果。
- ReAct = 循环：思考(Reason) → 行动(Act) → 观察(Observe) → 再思考。
- harness 的角色：执行工具、把结果回填、让模型"看到"结果继续思考。

## 二、协议铁律：tool_calls 配对回填

1. assistant 消息带 tool_calls 后，必须紧跟一一对应的 tool 消息，
   靠 `tool_call_id` 配对（loop.py:235-241 点单、loop.py:304-310 回填）。
2. 漏一条、错 id、中间插内容 → API 400。
3. 这也是 main.py 存档前清洗"孤儿 tool_calls"的原因（第 7 层）。

## 三、双层循环结构

```
外层 for i in range(50)   → 一轮 = 一次完整"想→做→看"
内层 while True           → 空转/截断原地重试（不耗外层轮次）
```

- 外层 max_iterations=50：任务执行空间（config.yaml）
- 内层 stall_limit=5：单轮内失败重试预算
- 设计动机：重试 ≠ 完成一轮。分开管理两种预算。

## 四、止损体系（stall_count 共用一个计数器）

| 形态 | 判定 | 位置 |
|---|---|---|
| 截断 | finish_reason=length | loop.py:170 |
| 空转 | 无内容输出 | loop.py:185 |
| 重复输出 | 连续相同 stop 内容 | loop.py:330 |
| 静默点单 | 连续 2 轮无文字说明 | loop.py:205 |

- 四种形态共用 stall_count：本质都是"模型卡住"，共享计数形成兜底网络，
  防止轮换卡死（截断2+空转2+重复2 无限循环）。
- 累计 5 次 → `_abort` 返回中止消息。
- 例外：静默点单用独立计数器 silent_rounds——有进展只是没播报，只提醒不中止。
- 截断/空转的重试方式：注入 user 消息（系统提示）→ continue。
  提示本身就是"往 messages 里塞消息"哲学（第 0 层决策 1）的体现。

## 五、其他设计点

## 六、思考题与答案

**Q1：为什么 tool 回填消息必须用 tool_call_id 与点单配对？乱序或缺失会怎样？**
A：OpenAI 协议硬性校验：assistant.tool_calls 与 tool 消息必须 id 一一对应、
顺序紧跟。缺失（如审批被拒/中断留下无结果的点单）会导致恢复会话后
API 直接 400。所以 main.py 存档前有"孤儿 tool_calls 清洗"——
协议约束决定了代码里必须有配套的防御逻辑。

**Q2：空转/截断重试放在内层 while 不耗外层轮次，为什么这么设计？**
A：这两种情况是"这次调用没成功"而非"一轮完成了"。若耗轮次，
网络波动空转几次就烧光 50 轮预算导致任务强制中止。分层本质是
**把两种预算独立管理**：单轮重试预算（5 次）与任务执行轮次（50 轮）。

**Q3：为什么截断/空转/重复输出共用一个 stall_count，而不是三个独立计数器？**
A：三者本质相同——模型陷入卡死状态，没有有效产出。若分开计数，
模型可以轮换形态（截断2次→空转2次→重复2次）无限卡下去，每个计数器
都达不到阈值。共享计数器是"止损兜底网络"：任何卡死形态累计 5 次即中止。
这是防牛角尖机制的核心设计。

**Q4：loop 只检测单轮内问题，为什么跨轮无进展检测放在 main.py:433-458？**
A：loop 每轮结束就返回，跨轮统计需要状态留在调用方（main）。
且 main 有 before_len 切片（main.py:411），能精确圈出本轮新增的 tool 消息
判断"是否全部失败"。职责边界：loop 管一轮内的生成质量，
main 管跨轮的任务进展——两者构成"单轮→跨轮"两级止损。

**Q5：silent_rounds 为什么不并入 stall_count？**
A：静默点单有实质进展（工具在正常干活），不是卡死，只是违反
"播报给用户"的交互约定。混入 stall_count 会误杀正常的长任务。
不同的失败等级用不同的计数器与不同的处置（提醒 vs 中止）。
