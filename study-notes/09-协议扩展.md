## 一、MCP 概念

- MCP = Model Context Protocol，让 harness 运行时动态接入外部工具生态。
- 类比：harness=手机，MCP=USB 接口+协议，MCP server=外接设备。
- 通信 = JSON-RPC 2.0 over stdio：
  - JSON-RPC：请求 {jsonrpc,id,method,params}，响应 {jsonrpc,id,result/error}。
  - over stdio：走标准输入/输出（每行一个 JSON），非网络。简单 + 进程隔离。

## 二、MCPServer 客户端（mcp.py）

- 启动流程：Popen 起进程 → initialize 握手 → list_tools 发现工具。
- `_request`（mcp.py:19-35）：同步一问一答，写一行 JSON、readline 读一行响应。
- 三个协议方法：initialize / tools/list / tools/call。

## 三、动态注册闭环（main.py:276-287）

## 六、思考题与答案

**Q1：MCP 为什么用 stdio（JSON-RPC）而不是 HTTP 网络调用？**
A：简单 + 进程隔离。stdio 无需端口管理、网络配置，本地进程管道即可通信；
一个 server 一个进程，崩溃/卡死可独立 kill 不影响主进程。缺点是只能本地
单机（不支持远程/分布式），对教学级 harness 足够。选型本质是"能力 vs
复杂度"的权衡。

**Q2：MCP 工具名加 mcp_ 前缀有什么作用？**
A：双作用。① 命名空间隔离：不同 server 的同名工具不冲突；② 权限标记：
第 5 层 permissions.py:35 靠 `startswith("mcp_")` 识别并默认放行。
一个前缀同时承担"命名空间"和"权限分级"两个职责。

**Q3：grep 正则编译失败为什么降级为字面量搜索而不是报错？**
A：容错降级。模型给的 pattern 可能不是合法正则（用户真实意图是字面量
搜索），直接报错会让模型重试浪费轮次。降级为 `pattern in line` 字面量
匹配，多数场景仍能得到有用结果。原则：宁可次优完成，不要失败（与
edit_file"宁失败不猜"是相反场景——搜索失败代价小、可重试；改文件失败
代价大、不可恢复，所以策略不同）。

**Q4：make_executor 为什么返回闭包而不是直接绑定函数？**
A：register_dynamic 要求 executor 签名是 executor(arguments)。闭包捕获
server 和 tool_name，返回符合签名的函数，MCP 工具与内置工具对
registry.execute_tool 完全同构。这是"统一工具协议"的落地——接入新生态
不改 loop、不改 registry 调用逻辑（第 3 层决策的回收）。

**Q5：MCP 工具默认放行（第 5 层）有什么风险？如何改进？**
A：外部 server 的工具被无条件执行，恶意或有 bug 的 server 可能带来破坏。
当前是教学级取舍：默认信任换简单。改进方向：给 MCP 工具也加审批、
来源白名单、或 sandbox 隔离。这提示了权限分级（第 5 层）在协议扩展
场景下的盲区。
