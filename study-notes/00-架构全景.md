# 第 0 层 · 架构全景 学习笔记

> 项目：mini-harness（个人 AI 终端助手）
> 核心命题：模型无状态，harness 补全记忆、手脚、循环与安全。

## 一、基础概念

### 1. LLM 调用 = 收发消息列表

- 请求：一串 messages（role + content 的字典列表）
- 角色：`system`（人设）、`user`（用户）、`assistant`（模型）、`tool`（工具结果，后续层出现）
- 响应关键字段：
  - `content`：模型说的话
  - `tool_calls`：模型的"工具单"（名字 + JSON 参数）
  - `finish_reason`：为什么停（stop=答完 / tool_calls=想用工具 / length=被截断）
  - `usage`：token 用量

### 2. 关键认知：模型无状态

API 服务器不记得历史，每次必须发完整 messages 列表。
→ "记忆"是 harness 不断 append 消息实现的（main.py:404）。

### 3. 关键参数

- `temperature`：随机度，0 保守 → 1 发散
- `max_tokens`：输出上限，超出即 finish_reason=length
- `stream`：True=边生成边收（流式），False=一次性完整返回

## 二、分层地图

| 层 | 文件 | 类比 | 职责 |
|---|---|---|---|
| 大脑层 | agent/（loop.py 心脏，266 行） | 意识循环 | ReAct：想→做→看结果→再想 |
| 模型层 | model/（client.py + streaming.py，115 行） | 声带 | 收发消息、流式解析、重试退避 |
| 手脚层 | tools/（15 个工具） | 手脚 | 读文件、跑命令、搜索等 |
| 展示层 | ui/tui.py | 脸 | rich 渲染 |
| 粘合层 | main.py（538 行） | 中枢神经 | 交互循环、slash、记忆、存档 |
| 支撑 | config/ sessions/ user_memory.md | 长期记忆 | 配置、存档、偏好 |

反直觉点：模型层最薄、大脑层最厚——调用模型只是一行库代码，
工程难点在"循环怎么转、什么时候停、坏了怎么办"。

## 三、一条消息的生命周期

```
用户输入 (main.py:329)
  → @file 展开 (main.py:401)
  → append 进 messages (main.py:404)
  → run_loop (main.py:413 → loop.py:82)
      → stream_chat_full 流式调用 (loop.py:147)
          → 文字实时经事件总线给 UI (loop.py:156)
      → 看 finish_reason (loop.py:167)
          ├─ tool_calls → 权限审批 (loop.py:251) → 执行 (loop.py:263)
          │               → 结果回填 role=tool (loop.py:304) → continue 再转
          ├─ length/空 → 截断重试，累计 5 次中止 (loop.py:170-199)
          └─ stop → 返回 (loop.py:347)
  → main: 跨轮无进展检测 (main.py:433-458)
  → 自动命名 / 提炼记忆 / 存档 (main.py:460-489)
```

## 四、三个贯穿全书的设计决策

1. **messages 是唯一状态**：没有 Agent 对象；工具结果、todo、系统提醒都是消息。
   → 可存档、可恢复、可审计。
2. **loop 管单轮，main 管跨轮**：loop 每轮返回，跨轮统计留在 main。
3. **副作用收口**：模型只"点单"→ registry 查表 → permissions 审批 → 才执行。

## 五、思考题与答案

**Q1：为什么 messages 要原地 append 修改（main.py:404、loop.py:304），而不是函数式返回新列表？**
A：因为 messages 是"唯一状态"——main 和 loop 操作的是同一个列表对象。
loop 里工具结果回填后继续循环，main 里还要把最终 answer 追加进同一列表用于存档。
如果函数式返回新列表，调用方要手动合并，容易漏消息、丢存档数据。
原地修改 + 单一列表引用 = 状态永远完整，随时 save_session 都能拿到全量历史。

**Q2：事件总线 bus.emit 为什么要存在？loop 直接 print 不行吗？**
A：直接 print 会把"大脑"和"脸"焊死。事件总线让 loop 只负责"发出事实"
（emit("text")、emit("tool_call")），谁关心谁订阅：tui 订阅后渲染消息流、
工具卡片、diff 高亮；未来换 UI（如 Web）不用改 loop。
这就是发布-订阅模式解耦（第 8 层细讲）。

**Q3：config.yaml 的 max_iterations: 50 和 main.py:416 默认值 5，实际生效哪个？为什么差 10 倍？**
A：实际生效 50。main.py:416 用 `agent_cfg.get("max_iterations", 5)` 从 config 取值，
5 只是"配置文件里没写时"的兜底默认。差 10 倍的原因：50 是给复杂任务（多步骤、
需要几十次工具调用）的执行空间；5 是早期教学 demo（day4）阶段的保守默认，
项目成熟后改成 50 并写进配置。教训：**默认值和配置值要区分，
默认值是"最坏情况下的安全值"，配置值是"真实业务需求"**。
