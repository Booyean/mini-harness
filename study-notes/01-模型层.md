## 一、两种调用方式

| | 非流式 stream=False | 流式 stream=True |
|---|---|---|
| 响应 | 一个完整 JSON | 一串 chunk 碎片（SSE 协议） |
| 字段 | `message` | `delta`（只含新增部分） |
| 体验 | 等全部生成完才显示 | 逐词实时显示 |
| 用途 | 内部小调用（起标题、提炼记忆、compact） | 交互主对话 |

- SSE（Server-Sent Events）：HTTP 响应不关闭，服务器持续推送 `data: {...}`。
- openai 库把 SSE 封装成普通迭代器：`for chunk in stream`。
- 最后一个 chunk 无内容，只带 `finish_reason`。

## 二、chunk 结构三态

```
delta.content 非空        → 普通文字增量，逐片 yield "text"
delta.tool_calls 非空     → 工具调用碎片，按 index 累积
finish_reason 非 None     → 结束信号：stop / tool_calls / length
```

## 三、tool_calls 分片拼接（全书第一个难点）

1. 协议设计：arguments 是**字符串碎片**不是 JSON 对象——
   生成中任意时刻它都不是合法 JSON，无法当对象传输。
2. 拼接三规则：
   - `index` 区分并行的多个工具调用，各自独立累积
   - `id`/`name` 只出现在第一片 → 用 `if tc_delta.id:` 判断式赋值
   - `arguments` 出现无数次 → 用 `+=` 累加（绝不能 `=`）
3. 流结束后按 index 排序整理（streaming.py:47-56），此时才可 `json.loads`。
4. 经验：协议字段"只出现一次 vs 多次出现"决定了用 if 赋值还是 += 累加。

## 四、重试退避（client.py:15-24）

- 指数退避：`wait = 2 ** attempt` → 1s/2s/4s。限流时等待翻倍给服务器喘息。
- 只重试 RETRIABLE_ERRORS（超时/连接/限流）——"重试可能成功"的错误。
- 400/401 等 APIError 直接抛——重试无意义。
- 最后一次失败 `raise` 交给上层（main.py:428 捕获后提示用户检查网络/Key）。

## 五、stream_chat_full 生成器设计

- 一个生成器，两类产出：
  - `yield "text", 片段` → UI 实时渲染（要实时性）
  - `yield "done", 汇总` → loop 做分支决策（要完整性：tool_calls 全量、finish_reason）
- 思路：把"实时性"和"完整性"两个需求解耦给两个下游。

## 六、思考题与答案

**Q1：为什么流式协议里 arguments 必须是字符串碎片，而不是直接传对象？**
A：对象必须是合法 JSON。而生成过程中任何一个时刻，参数都处于
"半个 JSON"状态（缺逗号、缺引号、缺右括号），协议层无法解析成对象。
所以设计成"字符串 + 客户端拼接"，拼完整后才能 json.loads。
这揭示了流式协议的核心原则：**增量数据的完整性由客户端负责**。

**Q2：为什么只重试超时/连接/限流这三类错误，400（参数错）不重试？**
A：重试的价值建立在"错误是暂时的、下次可能成功"上。网络类错误（超时、
断连、限流）本质是暂时性的，等几秒再试大概率恢复。而 400/401 是**确定性错误**：
参数错了、key 错了，重试一万次结果都一样，只会白白浪费时间和配额。
所以 RETRIABLE_ERRORS 白名单（client.py:6）刻意收窄。

**Q3：stream_chat_full 为什么不只 yield "done"，把完整结果一次给出去？**
A：那样就退回非流式体验了——UI 要等到模型全部说完才能显示第一个字，
用户面对 30 秒黑屏。yield "text" 让 UI 逐字渲染（流式的全部意义），
yield "done" 让 loop 拿到拼装好的完整 tool_calls 做分支决策。
两个下游各取所需，是一个生成器服务两个消费者。

**Q4：模型一次点多个工具时，chunk 的碎片顺序可能交叉（index 0 和 1 交替出现），为什么代码还能正确拼接？**
A：因为按 index 分别累积（`tool_calls_acc[idx]` 每个 key 一个独立累积器），
碎片到达顺序无关紧要，最后 `sorted(tool_calls_acc.items())` 按 index 排序输出
（streaming.py:55）。这正是用"字典按 key 累积 + 最后排序"而不是"列表顺序追加"的原因。
